# C 代码规范

[返回项目首页](../README.md) · [文档索引](README.md)

## 文件与目录

- 文件夹统一使用全小写；由多个单词组成时使用小写蛇形，例如 `drivers/`、`flight_control/`、`system_services/`。
- C 源文件和头文件使用小写蛇形命名，例如 `flight_control.c`。
- 一个模块通常由同名 `.c` 和 `.h` 文件组成。
- 头文件只公开外部需要的类型、常量和函数。
- 私有函数与私有变量保留在 `.c` 文件中，并使用 `static`。
- CubeMX 生成文件仅在指定用户代码区域内修改。

## 类型与常量

| 对象 | 规则 | 示例 |
|---|---|---|
| 结构体类型 | 小写蛇形，以 `_t` 结尾 | `imu_sample_t` |
| 枚举类型 | 小写蛇形，以 `_t` 结尾 | `flight_state_t` |
| 枚举成员 | 大写蛇形 | `FLIGHT_STATE_DISARMED` |
| 宏 | 大写蛇形 | `CONTROL_RATE_HZ` |
| 编译期常量 | 大写蛇形或模块内 `static const` | `MOTOR_COUNT` |
| 布尔变量 | 使用 `is_`、`has_`、`can_` 等前缀 | `is_armed` |

优先使用 `stdint.h` 中的定宽类型，例如 `uint8_t`、`int16_t` 和 `uint32_t`。表示物理量时优先使用 `float`，并在接口注释中说明单位。

## 函数与变量

| 对象 | 规则 | 示例 |
|---|---|---|
| 公共函数 | `模块_动作` 的小写蛇形 | `imu_read_sample()` |
| 私有函数 | 小写蛇形并声明为 `static` | `static void update_bias()` |
| 局部变量 | 简洁的小写蛇形 | `gyro_rate` |
| 函数参数 | 小写蛇形 | `sample_time_s` |
| 全局变量 | 使用 `g_` 前缀 | `g_flight_state` |
| 文件内静态变量 | 使用 `s_` 前缀 | `s_last_update_us` |
| RTOS 句柄 | 名称说明对象类型 | `g_control_task_handle` |

- 手写代码中，`for` 循环的独立递增表达式统一使用后置自增，例如 `i++`、`index++`；递减同样使用 `i--`，不改变循环方向或判断条件。
- 不强制把所有循环变量命名为 `i`。自增结果参与其他运算时按实际语义处理，不机械替换；自动生成代码和第三方参考代码保留原有风格。

变量命名同时遵循以下两条原则：

1. 数学公式内部使用该领域通用的标准短变量，例如 `q0`～`q3`、`ax`、`gx`、`ex`、`dt`、`k`。这些名称只用于作用域较小、公式含义明确的局部计算。
2. 跨函数接口、结构体成员、模块状态和物理量使用清楚完整的名称；物理量应带单位后缀，例如 `acc_x_g`、`gyro_x_dps`、`voltage_v`、`sample_time_s`。

短变量只用于标准数学符号，不随意缩写普通业务变量。同一组短变量在文件中大量重复使用时，应在文件开头集中说明其含义和单位。其他变量应表达含义，避免使用 `data1`、`temp2`、`flag3` 等无法判断用途的名称。

变量作用域按以下顺序优先选择：

1. 函数局部变量：默认选择，作用域最小。
2. 函数内 `static` 变量：仅在函数确实需要跨调用保存状态时使用。
3. 文件内 `static` 变量：用于模块私有状态，使用 `s_` 前缀。
4. 跨文件全局变量：最后选择，仅在确实需要被多个模块直接共享时使用 `g_` 前缀。

跨模块数据优先通过函数接口、消息队列或明确的数据结构传递。原则上不在头文件中公开可被任意修改的 `extern` 全局变量。RTOS 句柄若只在本文件使用，同样应声明为文件内 `static` 并使用 `s_` 前缀；只有确实跨模块共享时才使用 `g_`。

## 函数传值

- 单个简单结果直接使用函数返回值。
- 函数只执行操作、不产生结果时返回 `void`。
- 普通数值输入直接按值传递。
- 多个相关结果整理成结构体，通过结构体指针输出。
- 函数可能失败时返回状态，实际数据通过指针输出。
- 较大的只读数据使用 `const` 指针传入。
- PID、滤波器等需要修改内部状态时，通过状态结构体指针传入。
- 数组和缓冲区通过指针传递，并同时传入长度。
- 不使用全局变量代替正常的参数和返回值传递。

总体原则：单个结果直接返回；多个结果使用结构体；需要报告错误时返回状态并通过指针输出。

## 头文件引用

- `.h` 文件只引用公开接口所必需的头文件。
- `.c` 文件首先引用自身对应的 `.h` 文件，再引用实现中直接使用的其他头文件。
- 使用某个模块提供的函数、变量或类型时，直接引用该模块的头文件，不依赖间接包含。
- 仅在 `.c` 文件中使用的 HAL、FreeRTOS 和硬件驱动头文件，不放入公共 `.h` 文件。
- 公共 `.h` 文件尽量不暴露 HAL、FreeRTOS 等底层类型。
- 每个 `.h` 文件必须具有独立的头文件保护，并且能够被单独引用。

总体原则：`.h` 文件描述模块对外提供什么，`.c` 文件包含模块内部如何实现。

## 接口与错误处理

- 函数只承担一个清晰职责。
- 公共函数说明输入、输出、单位和可能的错误。
- 驱动函数应返回明确的状态，不静默忽略 HAL 错误。
- 指针参数在使用前检查有效性。
- 数组接口同时传递容量或元素数量。
- 避免未经限制的等待循环，硬件访问必须考虑超时。
- 不使用魔法数字；硬件地址、频率和阈值使用有名称的常量。
- 不在实时控制路径中动态分配内存。
- 不在高优先级任务和中断中使用大量 `printf`。

## 注释与格式

- 手写代码的说明性注释统一使用英文，README 和设计文档使用中文；作者姓名保留原文，第三方和自动生成代码保留原有风格。
- `.c` 和 `.h` 的文件头统一使用 Doxygen 格式，包含 `@file`、`@brief`、`@author` 和 `@date`；日期记录文件创建日期。
- 公共函数的接口说明写在 `.h` 声明前，`.c` 定义处不重复；私有 `static` 函数的说明写在 `.c` 定义前。
- 函数注释按需要使用 `@brief`、`@param`、`@param[out]`、`@return` 和 `@note`，不为凑格式添加无意义内容；简单函数一句话即可，`void` 函数不写 `@return`。
- 接口说明应简要交代用途、输入输出、物理单位、取值范围和失败含义；阻塞行为、初始化前提或内部状态等容易遗漏的限制放在 `@note`。
- 结构体成员在定义处说明不直观的单位、缩放比例、范围和状态位；含义清楚的普通局部变量无需逐个注释。
- 私有状态变量仅在用途或生命周期不明显时，在声明处说明；数学短变量大量重复使用时，在 `.c` 文件开头集中说明其含义和单位。
- 函数内部只对不直观的算法、设计原因和限制添加注释，不逐行翻译代码；同一信息只维护一处，修改代码时同步更新对应注释。
- 使用项目统一的 `.clang-format` 自动格式化。
- `#include` 先放自身头文件，其余按标准库、平台库、项目模块分组。
- 提交前清除无效注释代码、临时打印和无意义警告。
